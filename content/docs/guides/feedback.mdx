Four things sit under the content of each docs page: the feedback widget, the edit link, the last updated date and the previous and next links.

## Feedback widget

The widget asks "Was this page helpful?" with a thumbs up and a thumbs down button. Each button shows how many votes it has.

1. Clicking a button sends one vote through the server action `submitFeedback` in `src/modules/feedback/server/submit-feedback.ts`. It validates the input with Zod and passes it to `handleFeedback`, which saves it and returns the new totals.
2. The counts are fetched when the page loads with `getFeedbackCounts`, and replaced by the totals the vote returns.
3. The vote is remembered in the browser's `localStorage`, and both buttons are disabled for that page afterwards. This is a convenience, not protection: clearing storage allows another vote.

If saving throws, the widget shows "Feedback could not be saved. Try again later." and logs the error on the server.

The submitted data is:

<TypeTable
  type={{
    url: { type: "string", description: "The page path, starting with a slash.", required: true },
    rating: {
      type: '"helpful" | "not-helpful"',
      description: "The button that was clicked.",
      required: true,
    },
  }}
/>

### Where feedback goes

`handleFeedback` passes each submission to the store exported from `src/modules/feedback/server/store.ts`. By default that is the console store. It logs a line to the server console and keeps the totals in memory, so the counts reset when the server restarts:

```txt
[feedback] {"url":"/docs/guides/theming","rating":"helpful","at":"2026-10-18T09:12:44.000Z"}
```

### Storing feedback in a database

Three database stores are optional modules. `docs-boilerplate init` asks which one to use, and `add` installs one later:

```bash
npx docs-boilerplate add feedback-postgres
```

The store module adds its file to `src/modules/feedback/server/stores`, points `store.ts` at it, adds its package to `package.json` and its variables to `.env.local`, then installs. Each store saves to a `feedback` table that it creates on the first submission:

| Module              | File          | Package                    | Environment variables                    |
| ------------------- | ------------- | -------------------------- | ---------------------------------------- |
| `feedback-postgres` | `postgres.ts` | `postgres`                 | `DATABASE_URL`                           |
| `feedback-neon`     | `neon.ts`     | `@neondatabase/serverless` | `DATABASE_URL`                           |
| `feedback-libsql`   | `libsql.ts`   | `@libsql/client`           | `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` |

Adding another store module switches to it, unless you changed `store.ts` yourself. `store.ts` is one line:

```ts title="src/modules/feedback/server/store.ts"
export { postgresStore as feedbackStore } from "./stores/postgres";
```

The table has the columns `id`, `url`, `rating` and `created_at`, one row per vote. Counts are a `group by rating` over the rows of a page. A table created by an earlier version also has a nullable `message` column, which is no longer written.

<Tab value="Postgres in Docker">

The module adds `compose.feedback.yml` to the project root. It starts Postgres 17 on port 5432 with a named volume:

```bash
docker compose -f compose.feedback.yml up -d
```

```bash title=".env.local"
DATABASE_URL=postgres://docs:docs@localhost:5432/feedback
```

</Tab>
<Tab value="Neon">

Create a database in the Neon console and copy its connection string. The Neon store talks to it over HTTP, which also works in serverless and edge functions.

```bash title=".env.local"
DATABASE_URL=postgresql://user:password@ep-example.eu-central-1.aws.neon.tech/neondb?sslmode=require
```

</Tab>
<Tab value="Turso or a local file">

Set the URL and token of a Turso database:

```bash title=".env.local"
TURSO_DATABASE_URL=libsql://your-database.turso.io
TURSO_AUTH_TOKEN=...
```

Without `TURSO_DATABASE_URL` the store writes to `feedback.db` in the project root, which is gitignored. A local file does not persist on serverless hosts such as Vercel.

</Tab>
</Tabs>

For anything else, such as a webhook or an analytics tool, write a store with a `save` and a `counts` function and export it from `store.ts`:

```ts title="src/modules/feedback/server/stores/webhook.ts"
import type { FeedbackStore } from "../../types";

export const webhookStore: FeedbackStore = {
  async save(feedback) {
    await fetch(process.env.FEEDBACK_WEBHOOK_URL, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ ...feedback, at: new Date().toISOString() }),
    });
  },
  async counts() {
    return { helpful: 0, "not-helpful": 0 };
  },
};
```

<Callout type="warn" title="No protection by default">
  The action accepts any well formed vote and has no rate limit, so the counts can be inflated. Add
  one in `handleFeedback` before connecting it to a database or anything that costs money or
  notifies people.
</Callout>

### Turning it off

Set `pageFooter: { feedback: false, ... }` in `site.ts`. The widget is removed from every page and the server action stays unused.

## Edit link

"Edit this page on GitHub" opens the page's source file on GitHub. The URL is the repository, the branch and `site.contentDir` followed by the page path, built by `repositoryFileUrl`.

| To                            | Do this                                             |
| ----------------------------- | --------------------------------------------------- |
| Hide it on every page         | `pageFooter: { editLink: false, ... }` in `site.ts` |
| Hide it on one page           | `editUrl: false` in the frontmatter                 |
| Point one page somewhere else | `editUrl: https://...` in the frontmatter           |
| Change the repository         | `repository` and `branch` in `site.ts`              |

The link is also hidden when the site has no repository. Pages generated by the changelog sync set `editUrl` to their source file. See [Publishing a changelog](/docs/guides/changelog).

## Last updated

The date is the last commit that touched the page's file, shown in UTC. Turn it off for every page with `pageFooter: { lastUpdated: false, ... }`. It is hidden for a page with no git history, which is also the case in a checkout with `--depth 1`.

When neither the edit link nor the date has anything to show, the footer is not rendered.

## Previous and next links

The links to the neighbouring pages come from the sidebar order. Hide them on every page with `pageFooter: { prevNext: false, ... }` in `site.ts`.
